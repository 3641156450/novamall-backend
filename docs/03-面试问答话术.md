## 一、项目介绍（三个版本，按面试官给的时间选）

### 30 秒版（自我介绍里带过）

> "我课余做了一个分布式电商后端项目 NovaMall。
> 技术栈是 Spring Boot 3 + Spring Cloud Alibaba，用 Nacos 做注册中心、Gateway 做网关，
> MySQL + Redis + RabbitMQ。
> 里面完整实现了商品多级缓存、下单的分布式事务、秒杀的高并发扣库存，
> 另外用 Python 写了个数据分析服务，用 Go 写了个压测工具。
> 代码和文档都在我的 GitHub 上。"

### 1 分钟版（面试官说"介绍一下你的项目"）

> "这个项目是一个分布式电商后端，我一个人从零设计实现的，分了 6 个微服务：
> 网关、认证、商品、订单、秒杀、任务调度。
>
> 我重点做了三块：
>
> 第一是**商品的缓存体系**。用了本地 Caffeine 加 Redis 的二级缓存，
> 另外分别处理了缓存穿透、击穿、雪崩三个问题——穿透用布隆过滤器加空值缓存，
> 击穿用分布式锁做双重检查，雪崩用随机 TTL 打散过期时间。
>
> 第二是**下单的分布式事务**。下单要同时写订单和扣库存，跨服务没法用本地事务。
> 我用的是本地消息表的方案：订单和消息在同一个事务里落库，
> 事务提交后再发 MQ，失败由定时任务重投，最终一致。
>
> 第三是**秒杀**。核心是 Redis Lua 脚本把'判断库存、判断重复购买、扣减'合成一个原子操作，
> 抢到之后发 MQ 异步落库做削峰，实测不超卖也不重复卖。
>
> 另外还做了基于注解的幂等、分布式锁和限流，抽成了公共模块，业务代码里一行注解就能用。"

### 3 分钟版（面试官明显感兴趣，追问细节时用）

在 1 分钟版基础上，每个点加一句"为什么这么做"：

> "...缓存这块我为什么分两级：因为 Redis 再快也是一次网络往返，
> 爆款商品 QPS 高的时候网络开销就是主要瓶颈，
> 本地缓存命中率能到 90% 以上。代价是各 JVM 之间会有几十秒的不一致，
> 所以我只把商品详情这种能接受短暂脏读的数据放本地缓存，
> 库存这种强一致的数据坚决不放。"

> "...分布式事务为什么不用 Seata：AT 模式虽然一个注解就能用，
> 但它全程持有数据库行锁，高并发下性能损耗比较明显，还要额外部署 TC 服务。
> 电商下单用户能接受几百毫秒的延迟，所以最终一致就够了。
> 如果是资金相关的核心链路，我会考虑 TCC。"

> "...秒杀为什么不用分布式锁：锁是串行的，一万个请求要排一万个队。
> Lua 脚本在 Redis 里单线程执行，天然原子，而且是并发进来每个都极快。
> 当然这个方案有局限：主从切换的时候可能丢锁，
> 生产环境我会用 Redisson 或者直接上 Redlock。"

## 二、高频技术问题 & 标准答案

### Q1：缓存穿透、击穿、雪崩的区别？你怎么解决的？

> "三个都是'请求打到数据库'，但原因不同：
>
> **穿透**是查一个**根本不存在**的数据，比如用 id = -1 刷接口，
> Redis 里一定没有，每次都落到数据库。我用布隆过滤器前置拦截，
> 另外加一层空值缓存兜底，因为布隆过滤器有假阳性会误放行。
>
> **击穿**是某个**热点 key 恰好过期**，这一瞬间几万个请求同时发现缓存没了。
> 我用分布式锁加双重检查：只有拿到锁的线程去查库，其他线程等一下直接读缓存。
> 拿到锁之后要再查一次缓存，因为等待期间别人可能已经写好了。
>
> **雪崩**是**大批 key 同时过期**。我在基础 TTL 上加了 20% 的随机抖动把过期时间打散，
> 另外做了缓存预热，避免系统刚启动时冷启动雪崩。"

### Q2：Redis 和 MySQL 的双写一致性怎么保证？

> "我用的是 Cache Aside 模式：**先更新数据库，再删除缓存**。
>
> 反过来先删缓存再更新 DB 会有很大的不一致窗口：
> 删完缓存、DB 还没更新完，这时一个读请求会把旧值重新写回缓存，
> 之后就一直是脏数据了。
>
> 先更新 DB 再删缓存也不是完美的，有个极小概率的窗口：
> 缓存刚好过期，读请求查到旧值，写请求更新完 DB 删了缓存，
> 然后读请求才把旧值写回去。我做了延迟双删兜底，
> 删完等 500 毫秒再删一次。
>
> 更彻底的做法是用 Canal 监听 MySQL binlog，自动去失效缓存，
> 这是我下一步想做的。"

### Q3：分布式锁怎么实现的？有什么坑？

> "基于 Redis 的 `SET key value NX PX` 加 Lua 实现。四个必要条件：
>
> 第一，**加锁要原子**。必须是 `SET NX PX` 一条命令，
> 不能先 SETNX 再 EXPIRE，中间宕机就永久死锁了。
>
> 第二，**解锁要原子**。'判断是不是自己的锁'和'删除'必须在 Lua 里一起做，
> 否则可能出现：A 判断是自己的锁，正准备删，这时 A 的锁刚好过期，
> B 加上了锁，然后 A 把 B 的锁删了。
>
> 第三，**value 必须是唯一随机值**，防止误删别人的锁。
>
> 第四，**要有过期时间兜底**，服务宕机了锁也能自动释放。
>
> 坑的话主要有两个：一个是**主从切换会丢锁**，
> 锁还没同步到从节点主节点就挂了；另一个是**没有看门狗**，
> 业务执行时间超过锁的超时时间，锁提前释放并发问题又回来了。
> 生产环境我会直接用 Redisson，它有自动续期。
> 我这个项目手写一遍是为了把原理搞清楚。"

### Q4：什么是幂等？你怎么做的？

> "幂等就是同一个请求执行一次和执行一百次，对系统状态的影响完全一样。
>
> 产生重复请求的原因有几种：用户连点、前端超时重试、MQ 重复投递、支付回调重复通知。
>
> 我用了三层：
> 第一层是**一次性 token**。下单前先申请一个 token 存 Redis，
> 下单时带上，服务端用 Lua 脚本'存在才删除'，删除成功才放行。
> 之所以用 Lua 是因为'判断加删除'必须原子，否则两个并发请求可能都通过判断。
>
> 第二层是**数据库唯一索引**，订单号建了唯一索引，这是最后一道防线。
>
> 第三层是**状态机**，支付回调重复通知时，
> UPDATE 语句里带 `status = 0` 的条件，第二次执行影响行数为 0，天然安全。"

### Q5：分布式事务你怎么做？为什么不用 Seata？

（见上面 3 分钟版，另外补充：）

> "本地消息表的核心是：订单和消息在**同一个本地事务**里落库，
> 所以'订单存在但消息没记录'这种情况不可能发生。
> 只要消息落地了，靠定时任务重试一定能发出去。
>
> 有个细节：发消息不能写在事务方法末尾直接发，
> 因为事务可能还没提交，消费者收到消息去查订单会查不到。
> 我是用 `TransactionSynchronization.afterCommit()` 保证提交成功后才发。"

### Q6：秒杀怎么防止超卖？

> "核心是 Redis Lua 脚本。扣库存要做三件事：判断库存够不够、
> 判断用户有没有买过、扣减加记录。拆成多条 Redis 命令会有并发问题——
> 两个请求都 GET 到库存 = 1，都去 DECR，就变成 -1 了。
>
> Redis 单线程执行 Lua 脚本，把三步合成一个就天然原子了，
> 而且只需要一次网络往返，比四条命令快四倍。
>
> 为什么不用分布式锁：锁是串行的，一万个请求排一万个队，QPS 掉到几百。
>
> 抢到之后不是同步写数据库，而是发 MQ 异步落库做削峰——
> MySQL 单行 UPDATE 的 TPS 就几千，秒杀瞬间几十万请求，
> 同步写会把连接池打满。
>
> 另外我处理了 MQ 发送失败的情况：必须把库存回补回去，
> 宁可少卖，不能让用户抢到了却没有订单。"

### Q7：项目里最难的/印象最深的问题是什么？

**选一个你真的踩过的**，这里给三个模板，挑一个符合你实际情况的：

> 模板 A（推荐，最真实）：
> "最开始我没用分布式锁，压测的时候发现库存会被扣成负数。
> 排查下来是两个请求同时查到库存 = 1，都通过了校验然后都去扣。
> 后来我把判断条件写进 UPDATE 的 WHERE 里，`WHERE stock >= num`，
> 由 MySQL 行锁保证原子性，影响行数为 0 就是库存不足。
> 这个事让我明白：**'先查再判断'永远有时序问题，判断必须和写操作放在一起**。"

> 模板 B：
> "我在本地怎么测都是对的，但多实例部署之后订单偶尔会被重复关闭。
> 查了很久才发现是定时任务在每台机器上都会跑一次。
> 后来加了 Redis 调度锁，谁抢到谁执行。
> 再后来我才知道这种场景应该用 XXL-Job，它还有分片的能力。"

> 模板 C：
> "用户信息串号。偶发的，本地复现不了。
> 原因是 ThreadLocal 用完没 remove，Tomcat 线程池复用线程的时候，
> 下一个请求读到了上一个用户的 ID。
> 加了 finally 里的 clear 之后就好了。
> 这类 bug 只在并发下偶发，特别难查。"

### Q8：为什么选择 XX 技术？（通用回答框架）

**不要说"因为大家都在用"或"因为它最火"**。用这个框架：

> 需求 → 候选方案 → 各自的代价 → 我的选择 → 什么情况下我会换

举例："为什么用 RabbitMQ 不用 Kafka？"

> "我的场景是订单异步化，消息量不大（日均几万条），
> 但需要**低延迟**和**可靠的投递确认**。
> RabbitMQ 的 confirm 机制、死信队列用起来很直接，运维也简单。
> Kafka 的优势是**吞吐量**（百万级）和消息回溯，
> 如果是日志采集、埋点数据上报这种场景我会选 Kafka。
> 订单量做大到百万级/天之后再考虑换。"

## 三、关于"这是不是你自己做的"

**这个问题一定会问，不要慌，也不要吹。可以这样答：**

> "是我自己一个人做的，前后大概花了 X 个月。
>
> 整体架构、技术选型、核心代码都是我自己写的。
> 缓存那套方案我是先看了 Redis 官方文档和一些技术博客，
> 理解之后自己实现的；布隆过滤器和分布式锁我是故意手写了一遍，
> 因为直接调 Redisson 的 API 学不到东西。
>
> 当然有些地方参考了别人的思路，比如本地消息表这个方案是业界成熟的模式，
> 我按自己的理解实现了一遍。
>
> 项目现在还有不少不足：没有做服务的多副本部署，压测也没做到特别高的量级，
> 认证这块内网调用的安全性做得比较简化。这些我在 README 里都写了。"

**这样说为什么好**：
1. 承认了参考和不足 → 可信
2. 说清了哪些是自己设计的 → 有能力
3. 主动指出局限 → 有判断力

## 五、不会的问题怎么答

**千万不要瞎编。** 三个万能句式：

1. **"这个我没有深入研究过，我的理解是……"**
   → 说出你确实知道的部分，然后停住

2. **"这个我在项目里没用到，但如果让我做，我会先……"**
   → 给出你的思路（哪怕不完整），展示方法论

3. **"这个我需要回去查一下资料。您能提示一下方向吗？"**
   → 真诚，而且把问题变成了交流

**例子**：面试官问"Redlock 的具体算法是什么？"

> "Redlock 我只了解大意：向 N 个独立的 Redis 实例依次申请锁，
> 超过半数成功且总耗时小于锁的有效期才算加锁成功。
> 具体的实现细节我没有深入研究过，
> 而且我知道这个算法在分布式系统领域还有争议，
> Martin Kleppmann 和 antirez 有过一次公开讨论。
> 这块我需要回去再看看。"

这个回答比瞎编好一百倍——它证明你有信息源、知道自己知识的边界。

## 六、反问环节（一定要问，而且要问得有水平）

挑 2~3 个问：

1. "咱们团队现在后端主要负责哪块业务？技术栈大概是什么？"
2. "新人入职后一般多久开始独立接需求？会有 mentor 带吗？"
3. "团队现在在技术上有比较想解决的痛点吗？比如性能、稳定性、或者是 legacy 代码？"
4. "如果我入职，前三个月您希望我重点补哪方面的能力？"
5. "咱们的发布流程大概是什么样的？有没有 CI/CD？"

**不要问**：加班多不多、薪资什么时候涨、能不能远程（第一轮别问）。
