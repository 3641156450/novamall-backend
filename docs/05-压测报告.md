## 〇、压测工具本机实测记录（2026-09-19，真实数据）

> 目的：验证自研压测工具 `novamall-go/bench` 的可用性与报告输出。
> 压测目标：本机一个 Python `http.server` 演示服务（**不是** NovaMall 业务接口），
> 所以这里的 QPS 只代表"工具能跑通、指标真实"，**不代表项目性能**，请勿写进简历。

```text

目标地址   : http://127.0.0.1:8080/api/product/10001
并发数     : 100
总耗时     : 20.166s
总请求数   : 10000
成功/失败  : 10000 / 0
QPS        : 495.88
平均耗时   : 200.215ms
P50        : 190.16ms
P95        : 282.237ms
P99        : 398.542ms
状态码分布 :
   200 : 10000

```

**结论**：工具在 Windows 下编译运行正常（`go build` 通过，`go vet` 无警告），
10,000 请求 100% 成功、指标齐全。这套命令和输出格式可以直接用于业务接口压测。

另外两个在本次实测中观察到的真实现象，面试可以直接当案例讲：

1. **listen backlog 太小导致大量连接被拒**：Python `http.server` 默认 `request_queue_size=5`，
   并发 200 时 99% 的请求连接被拒（压测报告里状态码 `0` 占绝大多数）。
   把 backlog 调到 1024 后成功率恢复 100%——和业务里"Tomcat 线程池 / 连接池打满"是同一类问题。
2. **并发过高时 P99 长尾急剧恶化**：300 并发时 P99 从 398ms 恶化到 2s 以上，
   印证了"加大并发后 QPS 不涨、延迟暴涨 = 已到瓶颈"。

## 四、瓶颈分析（跑完填）

按这个顺序排查：

1. **看 P99 和 P50 差多少**
   差很多（比如 P50=5ms、P99=200ms）说明有长尾请求，常见原因：
   - GC 停顿 → 看 GC 日志
   - 锁竞争 → 分布式锁等待
   - 慢 SQL → 开 MyBatis SQL 日志看耗时
   - 连接池打满 → 调大 HikariCP `maximum-pool-size`

2. **加大并发，看 QPS 还涨不涨**
   - 涨 → 还没到瓶颈
   - 不涨甚至下降 → 到瓶颈了
   - 下降 → 大概率是连接数/线程数过多导致上下文切换开销

3. **看错误率**
   出现大量超时/连接拒绝，说明某个资源被打满了（连接池、Redis 连接池、Tomcat 线程数）
