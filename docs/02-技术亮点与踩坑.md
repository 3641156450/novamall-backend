## 1. 缓存三兄弟：穿透 / 击穿 / 雪崩

**代码**：`ProductService`、`BloomFilterService`、`CaffeineCacheConfig`

### 1.1 缓存穿透 —— 查一个根本不存在的数据

**问题**：请求 `productId = -1` 或者随机的大数字。
Redis 一定没有 → 每次都打到 MySQL。被脚本持续刷，数据库直接被打垮。

**方案（本项目两层）**：
1. **布隆过滤器**：启动时把所有合法商品 ID 灌进 Redis Bitmap，请求先过一遍
2. **缓存空值**：即使过滤器放行、DB 也查不到，就在 Redis 写一个 `__NULL__` 标记，TTL 60 秒

**为什么两个都要**：
- 布隆过滤器有假阳性（会误放行），所以后面还得有空值缓存兜底
- 空值缓存单独用，被换着 ID 刷时会占大量 Redis 内存，所以需要布隆过滤器先拦掉大部分

**必被追问**：
- **Q：布隆过滤器为什么不能删除元素？**
  A：一个 bit 位可能被多个元素共同置 1，删它会影响其他元素。要支持删除得用
  Counting Bloom Filter（把 bit 换成计数器）。
- **Q：误判率怎么算？**
  A：`(1 - e^(-kn/m))^k`，其中 k 是哈希函数个数、n 是插入元素数、m 是 bit 数组长度。
  本项目 m = 2^27 ≈ 1.34 亿 bit（约 16MB），k = 8。
- **Q：生产环境用什么？**
  A：Redisson 的 `RBloomFilter`，它根据期望插入量和误判率自动算 m 和 k。
  这里手写是为了讲清原理。

### 1.2 缓存击穿 —— 热点 key 过期瞬间的并发风暴

**问题**：某个爆款商品缓存过期，这一瞬间几万个请求同时发现"缓存没了"，
全部去查数据库。

**方案**：Redis 分布式锁 + 双重检查（Double Check）

```java
lockValue = redisLockHelper.tryLock(lockKey, 3000, 10000);  // 最多等 3 秒
if (lockValue == null) { /* 自旋等一下，直接读缓存 */ }
try {
    // 双重检查：拿到锁后再查一次，前面的线程可能已经写好了
    cached = redis.get(key);
    if (cached != null) return cached;
    product = queryDb(id);
    redis.set(key, product, randomTtl());
} finally {
    redisLockHelper.unlock(lockKey, lockValue);  // 必须 finally
}
```

**为什么双重检查**：线程 B 等锁的 3 秒里，线程 A 已经把缓存写好了，
B 拿锁后不查缓存就直接查库，等于白等。

**追问**：
- **Q：还有别的方案吗？**
  A：逻辑过期。缓存永不过期，value 里存一个业务过期时间，
  发现过期就起异步线程去刷新，期间返回旧数据。好处是永远不阻塞用户，
  代价是有一小段时间数据不新鲜、实现复杂。
- **Q：你为什么不用逻辑过期？**
  A：商品详情属于"可以短暂等一下，但不要脏数据"的场景，互斥锁更合适。
  首页那种"越快越好、旧一点无所谓"的用逻辑过期更好。

### 1.3 缓存雪崩 —— 大批 key 同一秒集体过期

**问题**：如果所有商品缓存都在启动时写入、TTL 都是 30 分钟，
那 30 分钟后它们会**同时**失效。

**方案**：基础 TTL + 随机抖动

```java
private long randomTtl() {
    return BASE_TTL + RANDOM.nextInt((int) (BASE_TTL * 0.2));  // ±20%
}
```

**另外两层保险**：
- **缓存预热**：项目启动时把热点数据先加载进去（避免"冷启动雪崩"）
- **多级缓存**：即使 Redis 挂了，本地 Caffeine 还能扛一会儿

### 1.4 双写一致性

**结论**：**先更新数据库，再删除缓存**。

**为什么不是"先删缓存再更新 DB"**：
```
1. 线程 A 删缓存
2. 线程 B 读请求进来，缓存没有 → 查 DB 拿到【旧值】→ 写回缓存
3. 线程 A 更新 DB 为新值
结果：缓存里一直是旧值，直到 TTL 过期。脏数据窗口非常大。
```

**"先更新 DB 再删缓存"也不是完美的**：
```
1. 缓存刚好过期
2. 线程 B 查 DB 拿到旧值
3. 线程 A 更新 DB，删缓存
4. 线程 B 把旧值写回缓存      ← 极小概率，但存在
```
要兜底就做**延迟双删**：删一次，等 500ms 再删一次（本项目实现了）。

**追问**：
- **Q：延迟双删的 500ms 怎么定的？**
  A：经验值，取"一次主从同步延迟 + 一次读请求耗时"。
  更优雅的做法是发 MQ 消息去删，或者用 Canal 监听 binlog 自动失效缓存。
- **Q：为什么不更新缓存而是删除缓存？**
  A：更新缓存容易产生"两次写顺序颠倒"的问题；
  而且很多缓存值是从多张表算出来的，更新它的成本比直接删掉让它下次重建高得多。

## 2. 秒杀：不超卖、不重复买、扛得住

**代码**：`SeckillLuaScripts`、`SeckillService`

### 2.1 为什么用 Redis Lua 而不是数据库

MySQL 单行 UPDATE 的 TPS 大概几千；秒杀瞬间可能几十万请求。
同步写库 → 所有请求堵在连接池 → RT 飙到秒级 → 连接池耗尽 → 整个服务雪崩。

**方案**：请求进来只做 Redis 操作（几万 QPS），
抢到资格后发 MQ，按数据库能承受的速度异步落库——这就是**削峰填谷**。

### 2.2 为什么用 Lua 而不是分布式锁

用锁能保证原子，但锁是**串行**的：一万个请求排一万个队，QPS 掉到几百。
Lua 脚本是"并发进来、每个都极快"，因为 Redis 单线程执行脚本天然原子。

```lua
-- 判断库存 → 判断是否买过 → 扣减 → 记录用户，四步在 Redis 里一次性完成
if redis.call('exists', stockKey) == 0 then return -1 end      -- 活动不存在
local stock = tonumber(redis.call('get', stockKey))
if stock == nil or stock <= 0 then return 0 end                -- 售罄
if redis.call('sismember', boughtKey, userId) == 1 then return -2 end  -- 买过
redis.call('decrby', stockKey, 1)
redis.call('sadd', boughtKey, userId)
return 1
```

**追问**：
- **Q：Redis 扣减成功但 MQ 挂了怎么办？**
  A：先回补库存（把 Lua 回补脚本跑一遍），再提示用户"抢购失败，请重试"。
  宁可少卖，不能"用户抢到了但没订单"。
- **Q：一人一单用 Set 存用户，100 万人抢购会不会撑爆 Redis？**
  A：会。100 万个 userId 的 Set 大概几十 MB，能接受但要注意。
  真实场景会限购 + 限制活动规模，或者用布隆过滤器替代（有误杀风险，需要权衡）。
- **Q：怎么防脚本刷？**
  A：① 接口地址隐藏（先请求一个一次性的秒杀地址）
  ② 图形验证码 ③ 用户维度限流（本项目已实现） ④ 风控识别设备指纹。
- **Q：Redis 挂了怎么办？**
  A：直接降级返回"活动太火爆"。**绝对不能**在 Redis 挂掉时把流量放到数据库上。

## 3. 分布式事务：本地消息表 vs Seata vs TCC

**代码**：`LocalMessage`、`OrderService`、`LocalMessageRetryTask`

### 3.1 问题

下单要同时做两件事（写订单表 / 通知库存服务扣库存），
一个在本地 MySQL，一个在 MQ，**没法放在同一个事务里**：

```
先写 DB 再发 MQ：DB 成功、MQ 挂了 → 库存永远没扣 → 超卖
先发 MQ 再写 DB：MQ 成功、DB 回滚 → 库存多扣 → 少卖
```

### 3.2 方案：本地消息表

```
1. 开启本地事务
2.   插入订单（状态：处理中）
3.   插入本地消息表记录（状态：待发送）   ← 和订单同生共死
4. 提交事务
5. 发消息到 MQ
6. 成功 → 改"已发送"；失败 → 什么都不做
7. 定时任务扫描"待发送"的记录重投（指数退避）
```

**核心洞察**：第 2、3 步在同一个事务里，所以"订单存在但消息没记录"不可能发生。
只要消息落地了，靠重试一定能发出去。

### 3.3 三种方案对比

| 方案 | 一致性 | 侵入性 | 性能 | 适用场景 |
|---|---|---|---|---|
| **本地消息表** | 最终一致（秒级延迟） | 中（要建表 + 定时任务） | 高 | 电商下单、发券、通知 |
| **Seata AT** | 接近强一致 | 低（一个注解） | 中（全程持有行锁） | 中小并发、要求简单 |
| **TCC** | 强一致 | 高（每个操作写 3 个方法） | 高 | 资金、账务核心链路 |
| **Saga** | 最终一致 | 高（每个操作写补偿方法） | 高 | 长流程业务（订机票+酒店） |

### 3.4 关键实现细节

**为什么用 `TransactionSynchronization.afterCommit()` 而不是在方法末尾直接发？**
```java
@Transactional
public String createOrder(...) {
    ...
    rabbitTemplate.convertAndSend(...);   // ← 错！事务可能还没提交
    return orderNo;                        //    消费者去查订单，查不到
}
```
消息发出去后消费者立刻查订单，此时事务还没提交 → 查不到 → 业务逻辑出错。

**为什么重试用指数退避？**
MQ 真的挂了时，如果每秒重试几千次，会把应用线程和网络都打满。
`2^n` 秒退避（1s、2s、4s、8s、16s）能自动降低重试频率。

**追问**：
- **Q：消息重复投递怎么办？**
  A：消费端必须做幂等。本项目用 `SETNX mq:consumed:{orderNo}` 去重。
  **发送端可靠 + 消费端幂等，缺一不可。**
- **Q：为什么不直接用 RocketMQ 的事务消息？**
  A：可以，RocketMQ 的半消息机制本质上就是把"本地消息表"做到了 MQ 里。
  本项目用 RabbitMQ（没有事务消息），所以自己实现了一遍表 + 重试。
- **Q：消息一直发不出去怎么办？**
  A：超过最大重试次数后状态置为"发送失败"（status=2），
  触发告警，人工介入或由补偿任务把订单关掉并回补库存。

## 4. 幂等设计

**代码**：`Idempotent`、`IdempotentAspect`、`OrderService`

### 4.1 为什么需要

- 用户手抖连点两次提交
- 前端超时重试 / 网关重试
- MQ 消息重复投递（ACK 没送达）
- 支付回调被第三方重复通知

### 4.2 本项目方案：一次性 token + Redis Lua 原子消费

```java
// 下单前：申请 token
String token = UUID...; redis.set("idempotent:" + token, token, 5min);

// 下单时：Lua 脚本"存在才删除"，原子操作
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**为什么必须用 Lua**：先 `GET` 判断再 `DEL`，两个并发请求可能都通过判断。

### 4.3 各种幂等方案对比

| 方案 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| **Token 机制** | 表单提交、下单 | 语义清晰（"这次提交"） | 需要额外一次请求拿 token |
| **数据库唯一索引** | 任何场景的兜底 | 最可靠，数据库保证 | 冲突时要处理异常 |
| **乐观锁（version）** | 更新操作 | 无锁，性能好 | 高并发下大量重试 |
| **状态机** | 有状态流转的业务 | 业务语义天然 | 只适用于有状态的对象 |
| **分布式锁** | 防并发 | 直接 | 防不住间隔很久的重复提交；串行化降吞吐 |

**本项目用了三个**：token（主）+ 订单号唯一索引（兜底）+ 订单状态机（支付回调）。

**追问**：
- **Q：业务执行失败了，token 已经被删了怎么办？**
  A：重新申请 token 再提交。也可以失败后把 token 写回去，
  但那会引入"失败重试风暴"，要谨慎。

## 5. 分布式锁

**代码**：`RedisLockHelper`、`DistributedLock`、`DistributedLockAspect`

### 5.1 四个必要条件（面试必背）

1. **加锁原子性**：`SET key value NX PX expire` 一条命令搞定。
   不能先 `SETNX` 再 `EXPIRE`——中间宕机就永久死锁了。
2. **解锁原子性**：Lua 脚本"判断 value 再 DEL"，分两步会被别人插队。
3. **解锁正确性**：value 必须是唯一随机值，防止误删别人的锁。
4. **过期兜底**：即使服务宕机，TTL 也会自动释放锁。

### 5.2 为什么要抽成注解

不用注解时每个方法都要写"加锁 → try → finally 释放"，
复制 20 处总有一处忘了 finally（线上事故）。
抽成 `@DistributedLock` 后业务代码只有一行注解。

### 5.3 局限（建议主动说）

- **主从切换丢锁**：锁还没同步到从节点，主节点就宕机了。
  生产方案是 Redlock（多实例多数派）或 Redisson。
- **没有看门狗**：业务执行时间超过 leaseTime，锁会自动释放，并发安全问题又回来了。
  Redisson 的 `RedissonLock` 有自动续期（watchdog），本项目没有。
- **本项目的缓解**：切面里检测"业务耗时 > leaseTime * 0.8"时会打 WARN 日志，
  提醒你把 leaseTime 调大。

### 5.4 与 Redisson 对比

| | 自研（本项目） | Redisson |
|---|---|---|
| 可重入 | 自己写 Lua Hash 计数 | 内置 |
| 自动续期 | 无 | 有（watchdog） |
| 主从切换 | 会丢锁 | Redlock 可用 |
| 学习价值 | 高，能讲清原理 | 低 |
| 生产推荐 | 不推荐 | **推荐** |

## 6. 限流：令牌桶

**代码**：`RateLimit`、`RateLimitAspect`

### 6.1 四种算法对比

| 算法 | 原理 | 缺点 |
|---|---|---|
| 固定窗口计数 | 每秒允许 N 个 | **临界突刺**：00:59 打 100 次 + 01:00 打 100 次 = 2 秒 200 次 |
| 滑动窗口 | 把窗口切成小格分别计数 | 精度越高，要存的 key 越多 |
| 漏桶 | 以恒定速率出水 | 不能应对突发流量 |
| **令牌桶** | 恒定速率放令牌，桶容量允许突发 | — |

**本项目选令牌桶**：兼顾限流和体验（攒下的令牌能应对短时突发）。
Guava RateLimiter、Sentinel 默认都是它。

### 6.2 为什么必须放 Redis

Guava RateLimiter 是**单机**的。服务部署 4 个实例，实际放行量是配置值的 4 倍。
集群限流必须把计数放到共享存储。

### 6.3 限流维度

```java
GLOBAL  → 保护下游，整个接口共享配额
IP      → 防爬虫
USER    → 防恶意刷单，比 IP 精准（IP 可能是公司出口 IP）
CUSTOM  → SpEL 自定义
```

**本项目秒杀用了 USER 维度**：公司/学校出口 IP 是共享的，
按 IP 限流会把同一出口的几百个正常用户一起误伤。

### 6.4 熔断降级思想

```java
catch (Exception e) {
    log.error("限流脚本执行异常", e);
    return joinPoint.proceed();   // Redis 挂了就放行，不能全站拒绝
}
```
限流组件自己出问题时，**选择放行而不是全站拒绝**——这是降级的核心思想。

## 7. MQ 可靠性

**代码**：`RabbitMqConfig`、`StockDeductConsumer`

### 7.1 三个环节都不能丢

| 环节 | 保障手段 |
|---|---|
| 生产者 → Broker | `publisher-confirm-type: correlated` + 本地消息表兜底 |
| Broker 自身 | 交换机 / 队列 / 消息三者都 `durable=true` |
| Broker → 消费者 | `acknowledge-mode: manual`，业务成功才 `basicAck` |

### 7.2 为什么必须手动 ACK

默认的 auto ACK 模式下，Broker 一把消息推给消费者就认为处理完了、直接删除。
消费者刚拿到消息就宕机 → 消息永久丢失。

### 7.3 死信队列

**不要用 requeue 无限重试**。一条永远处理不了的消息会把整个队列堵死，
后面的正常消息全部出不来。

正确做法：失败 N 次后进死信交换机 → 死信队列 → 人工/补偿任务处理。

```java
args.put("x-dead-letter-exchange", DLX_EXCHANGE);
args.put("x-dead-letter-routing-key", DLX_ROUTING_KEY);
```

### 7.4 其他细节

- `prefetch: 10`：不限流的话，消费慢时会一次性把几万条消息拉到内存里，可能 OOM
- `x-max-length: 100000`：消费端全挂时防止把磁盘写满
- 消费端 `SETNX` 去重：发送端可靠 ≠ 消费端不会重复收到

## 8. 多级缓存

**代码**：`CaffeineCacheConfig`、`ProductService`

```
L1 Caffeine（JVM 内存，微秒级）→ 未命中
L2 Redis（毫秒级，集群共享）→ 未命中
L3 MySQL → 回填 L2 + L1
```

**为什么**：Redis 再快也是一次网络往返（0.2~0.5ms）。
爆款商品 QPS 几万时，网络耗时成为主要瓶颈，本地缓存能把命中率做到 90%+。

**代价（必须说）**：
- 本地缓存每个 JVM 一份，更新时无法像 Redis 那样"删一处全集群生效"
- 会有几十秒的短暂不一致
- 所以：本地缓存 TTL 要短（60s）；**库存这种强一致的数据绝不放本地缓存**

**为什么用 Caffeine 不用 Guava Cache**：
Caffeine 用 Window-TinyLFU 淘汰算法，命中率显著高于 LRU；
而且是 Spring Boot 3 默认支持的（Guava Cache 支持已被标记过时）。

## 9. 其他踩坑记录

| 坑 | 现象 | 解法 |
|---|---|---|
| ThreadLocal 串号 | 用户信息偶尔变成别人的 | 必须在 `finally` / `afterCompletion` 里 `remove()` |
| Feign 请求头丢失 | 下游拿不到 X-User-Id | 实现 `RequestInterceptor` 透传 |
| Feign 默认超时太长 | 下游一卡拖垮整条链路 | 配置 `connect-timeout: 2000` |
| MyBatis-Plus 分页失效 | total 永远是 0 | 必须配 `PaginationInnerInterceptor` 插件 |
| 多模块扫描不到 | 切面、全局异常不生效 | `@SpringBootApplication(scanBasePackages = "com.novamall")` |
| 金额用 double | 0.1 + 0.2 != 0.3 | 用 BigDecimal，且用 String 构造器 |
| BigDecimal divide | 无限小数抛异常 | 必须指定 `setScale(2, RoundingMode.HALF_UP)` |
| 响应式流没读响应体 | 连接不复用，`too many open files` | `io.Copy(io.Discard, resp.Body)` |
| 定时任务多实例重复执行 | 数据被处理 N 次 | Redis 调度锁，或上 XXL-Job |
| 逻辑删除 + 唯一索引冲突 | 删掉的用户不能重新注册 | 唯一索引带上 deleted 字段 |
