# 01 · 架构设计

## 一、服务拆分

按**业务领域**拆分，而不是按技术分层拆：

| 服务 | 职责边界 | 独立的数据表 |
|---|---|---|
| novamall-auth | 账号、凭证、角色 | `t_user` |
| novamall-product | 商品、分类、库存 | `t_product`、`t_category` |
| novamall-order | 订单、订单明细、本地消息 | `t_order`、`t_order_item`、`t_local_message` |
| novamall-seckill | 秒杀活动、秒杀库存 | `t_seckill_activity` |
| novamall-job | 调度任务（不拥有数据） | 无 |

**拆分原则**：每个服务拥有自己的表，其他服务只能通过接口访问——
这就是 "Database per Service"。novamall-job 不连业务库，只通过 Feign 调用，
就是这条原则的体现。

### 为什么不做成"一个单体"

| 维度 | 单体 | 微服务 |
|---|---|---|
| 开发调试 | 简单，一个进程 | 要起 N 个服务 + 注册中心 |
| 部署 | 改一行全量发版 | 单个服务独立发版 |
| 故障隔离 | 一个模块 OOM 整个挂 | 秒杀挂了不影响下单 |
| 团队协作 | 抢同一个代码库 | 按服务划分 ownership |
| 技术异构 | 只能用一种语言 | 可以 Python 做分析、Go 做工具 |

**诚实地说**：对于一个人开发的项目，微服务是**过度设计**。
商城这种体量，一个模块化的单体（Maven 多模块，单进程启动）开发效率会高得多，
线上问题也更好排查。本项目拆成微服务，主要是为了**展示对这些组件的理解和动手能力**。

> 面试时可以主动说这句话，再加一句"如果是真实的小团队项目，
> 我会先用模块化单体，等业务复杂到需要多团队并行时再拆"——
> 这比无脑喊"微服务好"成熟得多。

## 二、请求链路

以"用户下单"为例：

```
1. 前端 POST /api/order/create  (Header: Authorization: Bearer xxx)
        │
2. Gateway :8080
   ├─ TraceIdFilter      生成/透传 X-Trace-Id
   ├─ AuthGlobalFilter   解析 JWT → 查 Redis 黑名单 → 塞 X-User-Id 头
   └─ 路由到 lb://novamall-order
        │
3. Order :8083
   ├─ UserContextWebConfig   从 X-User-Id 还原 UserContext
   ├─ IdempotentAspect       Redis Lua 原子消费幂等 token
   ├─ DistributedLockAspect  拿分布式锁
   ├─ OrderService
   │    ├─ Feign → Product 服务批量查商品（带降级）
   │    ├─ 校验价格 / 库存
   │    └─ 本地事务：插订单 + 插明细 + 插本地消息
   └─ 事务提交后 → afterCommit 发 MQ
        │
4. RabbitMQ → novamall.stock.deduct.queue
        │
5. Product :8082  StockDeductConsumer
   ├─ Redis SETNX 去重（消费端幂等）
   ├─ 扣库存（UPDATE ... WHERE stock >= num）
   └─ 手动 ACK / NACK（失败进死信队列）
```

## 三、关键设计决策

### 3.1 认证放在网关统一做

**做法**：Gateway 的 `AuthGlobalFilter` 解析 JWT，把 userId / roleCode 放进内部请求头，
下游服务通过 `UserContextWebConfig` 还原到 ThreadLocal。

**好处**：签名算法变更只改一处；密钥只存在网关。

**代价与风险（要主动讲）**：
- 内网服务间调用绕过了网关，任何人能访问内网就能伪造 `X-User-Id` 头 → **水平越权**
- 缓解：服务部署在 VPC 内、Header 里传 JWT 而不是明文 ID、加内网 HMAC 签名
- 本项目为了简化用了明文 Header，代码注释里标明了这一点

### 3.2 授权用注解而不是 URL 规则

`@RequireRole("ADMIN")` 作用在方法上，比"配置 `/admin/**` 需要 ADMIN 角色"更细，
而且对**不走 HTTP 的调用**（定时任务、MQ 消费者）也生效。

### 3.3 分布式事务选最终一致，不选强一致

见 [02-技术亮点与踩坑](02-技术亮点与踩坑.md) 第 3 节，有完整的方案对比。

### 3.4 服务间调用用 Feign + 防腐层 DTO

订单服务里定义了自己的 `ProductDTO`，**不依赖**商品服务的 `Product` 实体。
原因：如果共享实体，商品服务加一个字段，订单服务就得改代码、重新编译、重新发版，
"独立部署"就没意义了。

### 3.5 库存扣减的三种场景，三种做法

| 场景 | 并发量 | 做法 | 代码位置 |
|---|---|---|---|
| 普通下单 | 低 | SQL 乐观锁：`UPDATE ... WHERE stock >= ? AND version = ?` | `ProductMapper#deductStock` |
| 秒杀 | 极高 | Redis Lua 原子扣减 + MQ 异步落库 | `SeckillLuaScripts` |
| 回补库存 | 低 | `UPDATE ... SET stock = stock + ?` | `ProductMapper#restoreStock` |

## 四、数据库设计要点

### 索引设计

```sql
-- 订单：超时关单任务的核心索引（status, create_time）
KEY idx_status_create_time (status, create_time)

-- 本地消息表：重投任务的扫描索引（status, next_retry_time）
KEY idx_status_next_retry (status, next_retry_time)

-- 商品：分类页查询（category_id, status）
KEY idx_category_status (category_id, status)
```

**联合索引的顺序原则**：区分度高的放前面，等值查询的放前面，范围查询的放后面。
`idx_status_create_time` 里 `status` 是等值（=0），`create_time` 是范围（< deadline），
所以 status 在前。

### 冗余字段

- `t_order_item` 冗余了 `product_name` / `price`：
  商品改名改价后，历史订单不能跟着变（财务和客服场景的基本要求）
- `t_product.sales` 冗余销量：
  避免每次展示都去 `COUNT` 订单表

### 逻辑删除

所有表都有 `deleted` 字段，MyBatis-Plus 的 `@TableLogic` 会自动在 SQL 里追加 `AND deleted = 0`。
**代价**：唯一索引必须带上 deleted 字段（如 `uk_username(username, deleted)`），
否则删掉一个用户后，同名用户再也注册不了。

## 五、如果换成 Spring Security 方案

本项目没用 Security 的完整过滤器链，改成那样需要：

1. 加 `spring-boot-starter-security` 依赖
2. 配置 `SecurityFilterChain`：
   ```java
   http.csrf(AbstractHttpConfigurer::disable)
       .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
       .authorizeHttpRequests(a -> a
           .requestMatchers("/api/auth/**").permitAll()
           .requestMatchers("/api/admin/**").hasRole("ADMIN")
           .anyRequest().authenticated())
       .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);
   ```
3. 自定义 `JwtAuthenticationFilter`：解析 token → 构造 `UsernamePasswordAuthenticationToken`
   → 塞进 `SecurityContextHolder`
4. 密码编码器用 `BCryptPasswordEncoder`（本项目已经在用了）

**取舍**：网关已经做了一次 JWT 校验，再在每个服务里跑一遍 Security 过滤器链是重复的；
而且 Security 的异常处理和我们自定义的 `GlobalExceptionHandler` 会打架（Security 的异常在
过滤器层抛出，`@ControllerAdvice` 拦不到，需要额外的 `AuthenticationEntryPoint`）。

## 六、容量估算（面试常被问）

> "你这个系统能扛多少 QPS？"

按单机 4 核 8G、Redis 单独部署估算：

| 接口 | 主要瓶颈 | 估算 |
|---|---|---|
| 商品详情（缓存命中） | Redis 网络往返 | 8000 ~ 15000 QPS（本地缓存命中可更高） |
| 商品详情（缓存未命中） | MySQL 主键查询 | 2000 ~ 5000 QPS |
| 下单 | MySQL 写 + 分布式锁 | 300 ~ 800 TPS |
| 秒杀抢购 | Redis 单线程 Lua | 30000 ~ 50000 QPS（Redis 上限） |

**说的时候一定要加前提**：这些是**理论估算**，我没有真实压测到这个量级。
实测数据见 [05-压测报告.md](05-压测报告.md) 的模板——**建议你真的跑一次填上真实数字**，
有真实数字的简历说服力完全不同。
